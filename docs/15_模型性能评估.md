## 原理详解

### 区分核心推理与端到端时间

一次业务请求不仅包含 `rknn_run`，还包含输入读取、预处理、数据拷贝、后处理、显示与排队。串行链路里总延迟近似为各阶段之和，而流水线处理帧率还受最慢阶段限制。报告时必须说明时间边界、图像尺寸、模型版本、NPU 核数和量化类型。

**判断标准：** 只能在完整流水线相同的条件下比较 FPS；单独 NPU 速度不等于实际视频 FPS。

### 采用可靠统计方法

首次执行可能初始化内部缓存，正式测试应先 warm-up，然后记录几十次以上的执行时延。中位数 p50 反映常态，p95 刻画慢请求。关注长期温度与功耗造成的降频，避免只摘最优一次数字。

**判断标准：** 写明重复次数、采样期、温度和计时起止点。

### 单变量性能优化

测得哪个阶段占用最大时间，才有资格决定优化方向。如果 decode/resize 过慢，升级 NPU 核数可能无用；如果 CPU NMS 过慢，应先看候选框数量和数据结构。每项优化后重新对比精度与延迟。

**判断标准：** 优化报告必须同时列出基线、修改项、耗时、任务级精度和验证条件。

## 实验与验证证据

### 实验 1：阶段计时

把输入、预处理、推理、后处理四阶段加上 monotonic 时间戳，计算各段耗时占比。

**检查结果：** 各段总和可以解释整体延迟。

### 实验 2：统计 p50/p95

固定同一输入，多次测试并排序时延，报告中位数与尾延迟。

**检查结果：** 附带样本数、warm-up 次数和温度。

### 实验 3：写比较报告

选择优化前后两种条件，除了目标变量外维持输入、设备和代码一致。

**检查结果：** 结果包含 FPS、NPU 时延、端到端 p95 和精度。

## 故障排查

### NPU 很快但总 FPS 很低

- 可能原因：摄像头帧率、CPU 后处理或输入输出复制是系统瓶颈。
- 验证动作：测各阶段耗时与队列长度。

### 测试跑久后变慢

- 可能原因：频率温度管理或资源泄漏。
- 验证动作：记录温度和 RSS、重复执行数据。

## 案例研讨

**问题：** NPU 平均只用 5ms，但应用只能处理 20FPS，应该先换模型吗？

**分析：** 不应直接换模型。先拆成采集、预处理、NPU、后处理和显示，分析最慢阶段并记录是否存在队列。假如 CPU 后处理需 25ms，那么只提升 NPU 很可能无法显著改善总帧率。

**证据：** 分段时延、端到端 FPS 和相同输入下的多次实验。

## 工程机理与知识深化

### 机制、公式与数据协议

端到端时延可拆成采集、预处理、内存传输、NPU 运行、后处理和呈现之和；FPS≈1/平均帧周期只适用于明确的串行/稳定吞吐模型，流水线并行时需另计时。以 wall-clock 运行外部命令得到的 `wall_ms` 包含进程启动、模型加载和销毁，不是 `rknn_run()` 单独耗时。p50 是延迟中位数，p95 是覆盖至少 95% 样本的分位值；需说明算法和样本量。

### 真实数值与工程例题

假设串行采集+预处理共 10ms、NPU 5ms、后处理 5ms，总时延为 20ms，理论串行上限约 50FPS；将 NPU 缩到 2.5ms 后，总时延 17.5ms，最多约 57FPS。4 个样本 [10,12,14,20]ms 的最近秩 p95=20ms，不能只报最小 10ms。

### 设计取舍和验收范围

对同一真实命令预热后采 30 次以上，报告 p50/p95/平均值、模型、温度和测量边界。若目标是 NPU core time，改用 SDK profiler/应用内分段打点；不要拿进程级 wall_ms 冒充纯 NPU FPS。

## 源码精读：关键 API、张量与验收

第 15 讲的 lesson_15.py 通过重复启动外部真实程序计算墙钟 p50/p95，重点是说清统计范围和样本数，不能将全进程运行时间误当作 NPU kernel 时延。

**数据路径：** `真实外部命令` → `预热若干次` → `重复执行与计时` → `CSV wall_ms` → `p50/p95`。

### 1. subprocess.run 测的是进程级墙钟时间

**输入：** 可执行文件、命令行参数与真实模型。**输出：** 每次启动、加载、执行及退出的总毫秒。

这种测量适合外部程序整体耗时，不隔离 RKNN 模型执行；与 SDK 内部的推理时间不是同一指标。

```python
start = time.perf_counter()
subprocess.run(cmd, check=True)
wall_ms = (time.perf_counter() - start) * 1000
```

### 2. 预热和重复采样

**输入：** --warmup 3、--runs 30。**输出：** 30 个测量点及其 CSV。

预热次数不计入统计样本；每次测量固定同一图片和模型，不可同时改变 NPU 核数和摄像头输入。

```bash
python3 examples/lesson_15.py --warmup 3 --runs 30 -- \
  /path/to/actual_demo /path/to/model.rknn /path/to/test.jpg
```

### 3. p50/p95 要与测量口径一起报告

**输入：** 排序后的 N 个 wall_ms。**输出：** 中位数和最近秩法 p95。

样本少时 p95 波动很大；采样间隔、温度、电源和 CPU/NPU 频率都可能影响结果。

```python
ordered = sorted(samples_ms)
p95 = ordered[math.ceil(0.95 * len(ordered)) - 1]
```

**数据例题：** 四个样本 10、12、14、20ms 按最近秩法 p95=20ms；这个例子只是统计计算，不是 RK3588 实测时延。

**验收边界：** 结果注明设备、模型、输入、warmup、runs 以及“外部进程总墙钟”口径；没有设备不能宣称测到 NPU FPS。
