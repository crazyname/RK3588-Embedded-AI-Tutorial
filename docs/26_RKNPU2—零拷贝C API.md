## 学习目标

- 理解通用 API 与零拷贝数据路径的不同

## 核心原理与工程设计

### 零拷贝究竟减少什么

常规推理可能经历 CPU 图片缓冲→预处理结果→NPU 输入缓冲的多次复制。所谓零拷贝通常指通过共享或可绑定的内存对象，减少某些阶段的冗余 CPU copy；不是所有处理步骤完全没有数据迁移，也不代表无需处理颜色、stride、对齐和缓存一致性。具体接口需参照本版本 `rknn_create_mem`、`rknn_set_io_mem` 等官方定义。

**理解检查：** 优化目标是端到端拷贝与延迟，不能只因 API 名称就声称实现零开销。

### 共享 buffer 的格式契约

输入 tensor 对 stride、dtype、layout、大小和物理/虚拟内存可见性可能有约束。图像宽度为 641 不代表每行只占 641×channels 字节，硬件对齐可能产生行 padding。若应用忽视 `w_stride`/size 或错误覆盖内存，可能出现错行、花屏甚至越界。

**理解检查：** 查询真实 tensor 属性及内存要求之后，再申请或绑定 buffer。

### 缓存同步和资源生命周期

CPU 写入共享数据后，NPU 需要看到最新内容；NPU 写输出后，CPU 读取前也可能需要适当同步。同步接口和所有权视 API、驱动与内存类型而定。内存池复用需避免一帧仍被 NPU 使用时另一线程覆盖；线程、DMA 和 NPU 的异步关系需要明确。

**理解检查：** 所有共享 buffer 必须有同步时序和唯一可判断的释放点。

## 工程机理与知识深化

### 数据契约与 SDK 工作机理

SDK 内存绑定路径通过 `rknn_create_mem` 分配模型可访问缓冲，再用 `rknn_set_io_mem` 将输入/输出绑定到模型，执行 `rknn_run` 后从绑定的输出内存读取结果。它能控制内存生命周期，但并不自动消除 CPU 到 SDK 缓冲的复制；与 V4L2 DMA-BUF fd → RGA 共享图像缓冲属于不同层次。

### 张量算例与完整数据路径

一个宽为 224、每行 RGB888 紧密 672 字节的图像，在 NPU native attr 需要额外行对齐时，内存需按 `size_with_stride` 分配，RAW 字节也必须与该布局相符；单纯 W×H×3 可能不够。性能测试必须比较同模型、同输入、同精度结果，区分 CPU memcpy、rknn_run 和总调用时间。

### 实验设计、取舍与判断

本课程把“普通 SDK 输入”“SDK 张量内存绑定”“摄像头 DMA-BUF 共享”分别验收。不能把 SDK create_mem 视为全链路零拷贝，也不能假定所有 cache flush/同步都是自动的；应遵守所用 SDK release 的内存契约。

## 源码精读：关键 API、张量与验收

本讲先讲普通输入与 SDK 内存绑定的区别，不把 DMA-BUF fd 导出或 RGA 加速误称为完整零拷贝。代码 rknn_zero_copy.cpp 是 SDK buffer 绑定教学。

**数据路径：** `CPU RAW 文件` → `rknn_create_mem` → `rknn_set_io_mem` → `rknn_run` → `读取绑定输出` → `rknn_destroy_mem`。

### 1. 普通路径：rknn_inputs_set()

**输入：** 普通用户内存中的 uint8 图像/RAW。**输出：** Runtime 接管或复制到适合 NPU 的缓冲路径。

这种调用简单，能作为结果正确性的基线；并不意味着一次 API 必然对应一次固定物理 memcpy。

```cpp
rknn_inputs_set(ctx, 1, &input);
rknn_run(ctx, nullptr);
rknn_outputs_get(ctx, 1, &output, nullptr);
```

### 2. 绑定路径：create_mem + set_io_mem

**输入：** native input attr / size_with_stride。**输出：** 与 Runtime 绑定的 rknn_tensor_mem。

SDK 可能要求按行 stride 对齐。raw.size 必须等于该实验查询的 native size_with_stride，不能用普通 W×H×C 盲目填充。

```cpp
auto *input_mem = rknn_create_mem(ctx, native.size_with_stride);
rknn_set_io_mem(ctx, input_mem, &input_attr);
// 把符合布局的像素拷到 input_mem->virt_addr
```

### 3. DMA-BUF 是另一个层次

**输入：** V4L2 导出 DMA-BUF fd。**输出：** RGA 可以导入 fd 作为图像源。

本仓库视频链在 RGA 输出之后仍有 CPU letterbox 和 rknn_inputs_set；因此不能叫摄像头→NPU 全程零拷贝。

```cpp
V4L2 --EXPBUF--> DMA-BUF fd --import--> RGA
RGA --CPU letterbox--> rknn_inputs_set --> NPU
```

**数据解释与练习：** 请画出普通路径、SDK 绑定路径、V4L2→RGA 的三种数据流，并分别圈出还存在 CPU 读写的地方；性能提升必须用相同模型/图片的真实测量判断。

**验收边界：** 板端用同一个输入比较普通接口与 SDK 绑定的输出是否一致；没有实机测试时只可写“原理与源码已理解”。

## 排错技巧

### 结果出现条纹/错位

- 根因：行 stride、padding、颜色格式或物理内存映射不匹配。
- 如何核对：逐行检查数据地址、像素格式及接口查询的 w_stride。

### 随机旧帧结果

- 根因：CPU-NPU 缓存同步遗漏或 buffer 被提前复用。
- 如何核对：绘制拥有者和同步时序图，加入独立帧内容核对。

## 工程案例

**情境：** 常规 API 正确，改用零拷贝后偶尔出现上一帧的检测结果。可能是算法不稳定吗？

**分析过程：** 首先排查 buffer 复用时序与缓存同步：应用可能在 NPU 读完前改写或 CPU 在必要同步前读到旧输出。依照当前 SDK 的内存与同步契约修正，验证连续多帧。

**提交证据：** 缓冲分配与同步流程、stride 属性、常规/零拷贝结果和分段耗时。
