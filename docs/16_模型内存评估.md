# 第16讲｜模型内存评估

> 自学重编版：结合权威资源，按原理→实验→诊断→验收学习。完整原视频转写保留在末尾。

## 学习目标

- 了解权重与中间特征的内存组成
- 使用 SDK 内存评估接口
- 区分模型文件大小和进程真实内存

## 原理详解

### 模型大小不等于实际内存

`.rknn` 是磁盘文件，运行时需要权重、中间激活张量、运行时上下文、输入/输出 buffer。图像解码、视频缓冲和系统进程额外消耗 RAM。Linux RSS 与 NPU 内部空间不是同一概念，应该分别记录文件大小、进程 VmRSS/VmHWM 和 SDK 提供的内存估算。

**判断标准：** 一款 80MB 模型在板端占用多于 80MB 并不异常。

### 需要关注峰值而不只是稳定值

初始化、首次推理、切换 shape 或并发开启模型上下文都可能导致短期峰值。板端设计不能把全部 RAM 分配给权重，应留操作系统、视频编解码和临时缓冲余量。

**判断标准：** 比较载入前、载入后、首次推理和长时间运行四个状态。

### 减内存会改变性能

量化模型、减少并发缓存或重用 buffer 可减小占用，但可能影响精度、吞吐或响应时延。每次改动都要记录内存峰值与业务指标，不能只看模型文件变小。

**判断标准：** 内存优化是否有效需要长期稳定测试与精度回归。

## 实验与验证证据

### 实验 1：建立内存基线

记录模型文件字节数、系统总内存、空载 MemAvailable。

**检查结果：** 结果标明磁盘空间和物理内存是不同单位/视角。

### 实验 2：监控运行峰值

对真实模型进程读取 `/proc/<PID>/status` 里的 VmRSS、VmHWM，在运行阶段取样。

**检查结果：** 获得初始化与执行中的峰值信息。

### 实验 3：设计并发预算

将模型、输入输出、帧缓冲与其他进程作预算，预留一定安全余量。

**检查结果：** 预算与实际观察值可对照。

### 参考片段

```bash
cat /proc/meminfo | head
# 用实际进程号替换 PID：
grep -E 'VmRSS|VmHWM|VmSize' /proc/PID/status
```

> 具体可执行条件需要按真实 SDK 与设备确认。

## 故障排查

### 偶发 OOM

- 可能原因：峰值 buffer 与多个并发模型叠加。
- 验证动作：记录 VmHWM 和系统 OOM 日志，查缓冲帧数。

### destroy 后 RSS 未马上归零

- 可能原因：内存分配器可能缓存已释放内存，不代表必然泄漏。
- 验证动作：重复创建销毁并观察趋势。

## 案例研讨

**问题：** 4GB RAM 的 RK3588 能放下 80MB 模型，为什么两个摄像头一启动就 OOM？

**分析：** 检查视频解码和高分辨率中间帧缓存的数量，连同模型上下文、系统服务和运行时中间 tensor 计算峰值。文件大小是非常不足的容量估计。

**证据：** 分段内存日志、帧缓冲估算和系统可用内存。
