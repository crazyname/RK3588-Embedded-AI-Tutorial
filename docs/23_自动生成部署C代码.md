## 学习目标

- 认识自动生成代码 API 的定位
- 分清 SDK 模板和模型专用后处理
- 将生成代码编译为可维护的板端程序

## 从原理到工程

### 生成代码只是起点

RKNN 的部署代码生成能力或官方模板可以缩短模型加载、输入输出属性查询、运行循环和资源释放等样板代码的开发时间，但并不知道所有业务数据的含义。图像格式、类别表、NMS、坐标映射、错误恢复和日志仍需按当前模型与应用场景自行实现。

**必须理解：** 编译通过不代表应用功能完成；要进行从图片到业务输出的完整验收。

### 阅读生成工程的结构

一个可维护项目通常分为主程序、模型上下文、预处理、执行器、后处理、工具函数和 CMake 工程。阅读时先找 `rknn_init` 和 `rknn_destroy` 的配对、输入 tensor 属性和错误返回，再追踪检测结果如何映射到图像坐标。

**必须理解：** 明确函数负责的资源和数据所有权，杜绝失败路径遗漏释放。

### 验证生成代码与具体 SDK

生成器接口、输出目录和工程结构与 SDK release 有关，应参考当前版本说明。平台 CMake 交叉编译时，头文件、动态库和目标工具链必须都属于正确的目标架构。生成代码需要实际板端功能测试和异常输入测试。

**必须理解：** 为工程准备良好的错误码和日志，并保存二进制架构检查输出。

## 实验与预期结果

### 实验 1：认识模板入口

在官方 Model Zoo 或 Toolkit2 的对应版本中查找 C/C++ demo 与代码生成说明。

**检查标准：** 记录原始仓库 commit、目标平台和导出文件列表。

### 实验 2：画调用关系

从 main 到初始化、query、输入、推理、取输出、后处理和销毁绘制调用图。

**检查标准：** 每处 `alloc/init/get` 有可追踪的 release/destroy。

### 实验 3：做异常场景表

列出模型文件不存在、错误 tensor shape、内存申请失败及 SDK 返回失败时的处理逻辑。

**检查标准：** 每种情况可以安全退出，不留下悬挂资源。

## 典型报错与诊断

### 生成项目编译成功运行失败

- 可能原因：模型与 runtime 不兼容、缺少动态库或输入属性错误。
- 定位方法：用 file/ldd/查询 tensor 属性逐步定位。

### 检测框缺失

- 可能原因：模板未实现当前检测头的解码、NMS 和坐标映射。
- 定位方法：核对模型输出语义与官方示例后处理路径。

## 案例演练

**问题：** 代码生成器输出的 demo 能初始化 RKNN，但图片始终没有检测框。是否生成器有 bug？

**作业证据：** 输入输出属性、业务后处理实现、样例图片与 expected outputs。

## 源码精读：关键 API、张量与验收

第 23 讲的 lesson_23.py 实际读取 ONNX 输入输出张量描述，生成可编译的 C++17 头文件 tensors.hpp，方便后续对接 RKNPU2；它生成的是接口元数据，不是完整 NPU 模型推理程序。

**数据路径：** `真实 ONNX 模型` → `graph.input/output shape 与 dtype` → `生成 TensorDescription` → `tensors.hpp` → `g++ 语法检查`。

### 1. ONNX：读取输入/输出张量描述

**输入：** graph.input 和 graph.output 中的 name、dtype、dims。**输出：** 每个张量的可读 shape 和类型编号。

输入的 ONNX dtype 编号不等于某个 RKNN SDK enum 的数值；遇到动态维度要保留字符串，不能一律写成固定 640×640。

```bash
python3 examples/lesson_23.py --onnx /path/to/model.onnx --output build/lesson23/tensors.hpp
```

### 2. 生成 TensorDescription 头文件

**输入：** 真实模型的 input/output 名称和维度。**输出：** namespace generated_model 中的 input_count/output_count 和 tensor_i。

生成结果只把图接口元数据封装成常量；它没有包含 rknn_init、rknn_run、内存分配和后处理，也不能直接加载 .rknn 文件。

```cpp
struct TensorDescription {std::string_view name; std::string_view dims; int dtype;};
// tensor_0 / input_count / output_count 由当前 ONNX 自动生成
```

### 3. --compile：使用 g++ 检查 C++17 语法

**输入：** 生成的 tensors.hpp、安装好的本机 g++。**输出：** 通过 g++ -fsyntax-only 的编译检查。

在 x86_64 PC 编译通过只证明这个 C++ 头文件合法，不等于可链接 ARM64 SDK，也不等于与 RKNN 转换后的实际张量契约一致。

```bash
python3 examples/lesson_23.py --onnx /path/to/model.onnx --output build/lesson23/tensors.hpp --compile
```

**数据例题：** ONNX 输入 (1,3,224,224)、输出 (1,1000) 时，生成器应包含一个 input_count 和一个 output_count；但真正 RKNN 模型的布局、量化 dtype 仍需要板端 rknn_query 确认。

**验收边界：** 对真实 ONNX 生成 tensors.hpp、检查输入输出名/shape 并用 --compile 完成 C++17 语法检查；完整 RKNPU2 程序在第 25 讲另学。
