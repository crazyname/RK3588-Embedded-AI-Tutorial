## 从原理到工程

### 静态尺寸与受限动态尺寸

动态 shape 意味着某些 tensor 维度可以变化，但在 RKNN 部署中是否支持、能变化到哪些规格、如何构建与选择，均依赖 SDK release、具体模型和目标 SoC。‘动态’不等于任意宽高无限制输入。很多硬件编译器会要求指定候选 shape 集合或对算子施加约束。

**必须理解：** 先看模型输入的实际支持集合，再调用运行接口。

### 布局和内存预算随 shape 改变

尺寸从 320×320 变为 640×640 时，空间像素数量扩大 4 倍，但总性能、内存和 NPU 时延不必然严格乘 4，因为算子结构、缓冲规划及融合也影响开销。不同分辨率可能改变目标检测的精度、感受野和后处理规模。

**必须理解：** 每个候选 shape 单独测准确率、输入 buffer 大小和延迟。

### 导出、转换、运行三阶段一致性

训练框架导出 ONNX 时若设置 dynamic，需确保下游算子、ONNX 图和 RKNN 转换器都能接受。最终以 RKNN 编译后的输入属性和实际运行接口为准，不能只根据 ONNX 符号维度判断板端支持。

**必须理解：** 使用明确的候选尺寸验证形状切换及输入/输出 buffer 生命周期。

## 实验与预期结果

### 实验 1：读取 ONNX 形状

使用 Netron/ONNX Python 打印 input 的 batch、高、宽，看是否是符号维度或固定整数。

**检查标准：** 能区分动态 ONNX 约束与 RKNN 的支持条件。

### 实验 2：计划两个 shape

针对同一模型设计 320 和 640 两套输入变换，计算输入 uint8 bytes 的变化。

**检查标准：** 宽高翻倍时原始同通道图像元素数增加四倍。

### 实验 3：按官方指南验证

若 SDK 当前支持动态 shape，使用其指定方式构建并分别运行每个支持规格。

**检查标准：** 记录每种 shape 的预处理、耗时、输出属性和正确性。

## 典型报错与诊断

### shape 不在支持集合

- 可能原因：编译时未声明或目标 SDK 未支持此形状。
- 定位方法：查询导出的 RKNN 属性与构建日志。

### 切换高分辨率后 OOM

- 可能原因：中间激活 tensor 和 buffer 需求增加。
- 定位方法：测目标 shape 的 VmHWM 和 SDK 内存指标。

## 案例演练

**问题：** 你导出 dynamic=True 的 ONNX 后，RKNN 模型仍只接受 640×640。是 ONNX 无效吗？

**思路：** 未必。ONNX 允许符号维度并不保证目标硬件编译器支持所有形状。需要按 SDK 的动态形状流程声明允许的规格，或者将源模型分别导出为固定尺寸构建。

**作业证据：** ONNX 输入维度、RKNN build 参数、实际报错以及成功的候选 shape。

## 源码精读：关键 API、张量与验收

动态 shape 指图的某些轴可以在运行时变化。lesson_21.py 在 ONNX Runtime 下用同一模型和多个实际 NPY 进行不同形状的推理，并保留每次 shape/耗时/输出形状；它不证明 RKNN 支持相同动态范围。

**数据路径：** `具有动态维度的 ONNX` → `输入 A 的 NPY` → `输入 B 的 NPY` → `相同 session.run` → `shapes.csv`。

### 1. 从 ONNX 检查符号维度

**输入：** session.get_inputs()[0].shape。**输出：** 含固定整数和动态符号的 shape 列表。

ONNX 的 dim_param 可能是 height/width 等符号，具体允许什么范围取决于模型算子和框架。不能仅仅将固定尺寸模型喂新尺寸称为动态。

```python
session = ort.InferenceSession('/path/to/dynamic.onnx')
print(session.get_inputs()[0].shape)
```

### 2. 对同一模型运行两个真实输入形状

**输入：** 两个与图 rank/dtype 匹配的 .npy 输入。**输出：** 每个 shape 的实际输出张量。

脚本依次调用 session.run，把一次 Python API 墙钟时间记到 CSV；这些毫秒含 Runtime 开销，并非 NPU 专用延迟。

```bash
python3 examples/lesson_21.py --onnx /path/to/dynamic.onnx --inputs /path/to/x320.npy /path/to/x640.npy --csv build/lesson21/shapes.csv
```

### 3. RKNN 是否支持动态输入要另行验证

**输入：** Toolkit2 版本、允许输入形状集合与目标板 Runtime。**输出：** SDK 认可的配置，或失败节点/不支持原因。

ONNX 模型声明动态维度不等于 RKNN 编译允许任意 shape；实际 RKNN 动态形状可能受版本、形状列表与内存约束。

**数据例题：** ONNX 同一模型接受 (1,3,320,320) 与 (1,3,640,640) 时，CSV 应包含两行不同 input_shape；若模型为固定 640×640，传 320 应报错而不是静默 resize。
