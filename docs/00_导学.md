## 技术原理精讲

### 一条完整的部署链

嵌入式 AI 并不等于在板上训练模型。典型流程是：收集或选择数据，在计算机训练与验证权重，再导出 ONNX 等交换格式，通过 RKNN-Toolkit2 面向目标芯片编译成 .rknn，最后由 RKNN Runtime 在 RK3588 的 NPU 上执行。摄像头采集、图像缩放、颜色转换、NMS 和绘图通常属于模型之外的业务程序。

**判断是否理解：** 同一张测试图在源框架、ONNX、RKNN 三处都应有可比结果；模型文件存在不代表任务完成。

### 自学时区分三台‘机器’

训练机可能配备 NVIDIA GPU，转换机通常要求与 Toolkit2 wheel 匹配的 Linux x86_64 环境，推理端则是运行 ARM64 Linux 的 RK3588 板卡。三者未必是三台独立物理机，但操作系统、处理器架构、Python 解释器、SDK 和运行库的约束不同。不要把开发机 wheel 安装到板端。

**判断是否理解：** 建立环境矩阵：任务、设备、CPU 架构、系统、Python、软件包版本、模型输出文件。

### 正确结果比成功运行重要

真实闭环至少包含模型语义正确、前后处理正确和资源可控三个层次。对于分类，检查标签是否映射正确；对于目标检测，检查框的位置、置信度和 NMS；对流式应用，关注平均帧率、延迟和长期温度。测试使用有标注的输入和明确的预期输出，避免凭肉眼只看一张图片。

**判断是否理解：** 用‘条件 → 操作 → 输出 → 判据’写实验日志，让另一个人能够重复你的实验。

## 跟做实验与验收证据

### 实验 1：盘点设备

查看板卡外壳型号、系统镜像发行信息、内存与摄像头/网络接口；建立 hardware.md，保存开发板型号及厂商提供的 BSP 下载位置。

**预期检查：** 记录的芯片型号应是 RK3588 或 RK3588S，系统信息与板卡标识可相互印证。

### 实验 2：准备三个工作区

分别创建 training、conversion、deployment 目录；在 README 中注明每个目录存放的模型、配置、图片和日志文件，不混放 wheel 与目标板运行库。

**预期检查：** 目录明确标识哪个文件在主机使用，哪个复制到 RK3588。

### 实验 3：画部署流程图

从一张图片开始，手写或使用 Mermaid 画‘读图 → 预处理 → 模型 → 后处理 → 输出’，并标注 ONNX 与 RKNN 的生成位置。

**预期检查：** 图上至少有主机模型转换、板端运行时和一处精度验证节点。

## 故障诊断

### 不知道该下载哪个 SDK

- 可能原因：混淆了旧版 RKNN-Toolkit 与面向 RK3588 的 Toolkit2。
- 诊断动作：先确认 SoC，再到 airockchip/rknn-toolkit2 和 rknn_model_zoo 的文档按版本选择。

### 转换成功但标签完全不对

- 可能原因：把模型转换当作全部部署工作，忽略了通道、归一化和类别表。
- 诊断动作：使用同一张图片分阶段核对张量尺寸、像素范围、输出前几项及类别索引。

## 自学案例分析

**情境：** 你拿到别人的 model.rknn 和一张图片，但不知道输入 shape 与类别表。可以直接把最大输出索引当成‘猫’吗？

**分析路径：** 不可以。首先询问模型任务、训练类别和预处理协议；通过 SDK 查询输入输出属性；用已知类别样本建立参考结果。没有标签映射时，索引只是数字，并没有可靠的语义。

**应交付证据：** 至少保留模型版本、输入属性、类别表来源、测试图片与对应输出。

## 源码精读：关键 API、张量与验收

这一讲不是把嵌入式 AI 说成一串术语，而是先用自己电脑的实际环境生成实验记录。lesson_00.py 只读取 Python、系统、开发工具与可选模型 SHA256，不会下载模型或操作开发板。

**数据路径：** `PC Python 解释器` → `平台、ABI 与 git/cmake/gcc` → `可选模型 SHA256` → `environment.json` → `后续实验基线`。

### 1. command_version()：查找并读取开发工具版本

**输入：** 工具名 git、cmake、gcc。**输出：** 是否安装、实际可执行文件路径、版本或错误说明。

命令存在不代表 RKNN SDK 兼容。用 shutil.which 判断是否找到工具，再执行 --version，固定日后复现用的版本。

```bash
python3 examples/lesson_00.py --output build/lesson00/environment.json
```

### 2. 环境清单：区分主机与开发板

**输入：** sys.version、sys.executable、platform.machine 等。**输出：** 包含 architecture、virtualenv、CPU 数及工具版本的 JSON。

x86_64 的 Toolkit2 环境与 aarch64 的 RKNNLite2 设备环境不同，单台 PC 记录不能被冒充为 ROCK 5B 记录。

```bash
python3 -c "import platform,sys; print(platform.machine(),sys.executable)"
```

### 3. --model：记录模型内容身份

**输入：** 可选真实 .onnx/.rknn 模型路径。**输出：** 文件路径、实际字节数、SHA256。

模型同名却版本不同会导致后续输入形状或类别不一致。摘要用于确认读到的究竟是哪一版，不代表文件合法或推理成功。

```bash
python3 examples/lesson_00.py --model /path/to/actual.onnx --output build/lesson00/environment.json
```

**数据例题：** 环境报告中显示 architecture=x86_64 时，说明这次记录的是主机；未连接 ROCK 5B 就没有资格勾选板端 NPU、相机、RGA 或 RKLLM 实测。

**验收边界：** 能够解释 JSON 的 Python 版本、CPU 架构、工具版本和可选模型哈希，并保存真实输出文件；没有模型也能完成环境初检。
