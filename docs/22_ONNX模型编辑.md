## 从原理到工程

### ONNX 图编辑的目的

图优化包括删除冗余算子、常量折叠、合理的节点融合、输入输出规范化与兼容性修改。但是 `Transpose`、`Reshape`、`Concat` 和 `Softmax` 都可能具有必要语义，不能因为看起来多余就直接删掉。图编辑前先保存原始模型和可信的 ONNX Runtime 基线。

**必须理解：** 任何图改写都需要语义保持证明，而不仅是 `checker` 通过。

### 形状重排如何影响语义

以 tensor 形状 [1,3,224,224] 为例，交换为 [1,224,224,3] 后元素数相同，布局语义不同。`Reshape` 通常改变组织方式而不显式交换数值轴；`Transpose` 会改变轴排列，两者不是可随意相互替代的操作。

**必须理解：** 在修改前给每个候选节点标出输入 shape、输出 shape 和 perm 属性。

### 正确的模型图回归

先运行 ONNX checker、shape inference，再用保存的输入样本对原/新 ONNX 分别运行推理，比较输出形状、最大绝对差、余弦相似度及任务级精度。只有验证通过后才能进入 RKNN 转换和真实 NPU 性能测试。

**必须理解：** 图更简洁不等于执行更快；优化有效性最终仍靠板端时延证明。

## 实验与预期结果

### 实验 1：检查输入图

选择一个有 Reshape/Transpose 的 ONNX，保存源文件 SHA256 与固定测试输入。

**检查标准：** 可追溯原模型来源和 tensor shape。

### 实验 2：执行安全静态检查

使用 onnx.checker 与 shape_inference 检查原模型，记录图中各节点数量。

**检查标准：** 无语法问题，未知维度被单独标注。

### 实验 3：做前后数值对照

在经过检验的 ONNX 编辑工具完成一个明确的常量节点整理，比较同样输入下的输出值。

**检查标准：** 用绝对误差/精度判断，避免凭图片观察。

## 典型报错与诊断

### 删除节点后输出异常

- 可能原因：节点实际上负责布局转换或后处理。
- 定位方法：在 Netron 确认数据轴和实际数值回归差异。

### checker 通过但 RKNN build 失败

- 可能原因：语法合法与硬件算子兼容是两个不同判断。
- 定位方法：查看 Toolkit2 不支持算子列表与实际 build 日志。

## 案例演练

**问题：** 删除 YOLO 检测头前的 Transpose 后，网络仍能导出 ONNX，框却全部偏移。为什么？

**思路：** Transpose 的轴变换可能是检测头解码所依赖的布局。当后处理继续按旧的轴含义读取 tensor 时，索引解释完全错乱。需要恢复节点或同步修改后处理，并通过回归测试验证。

**作业证据：** 编辑前后节点属性、输出 shape、同图数值和检测 mAP。
