## 原理精讲

### 转换 CLI 只是 SDK 的自动化入口

命令行转换工具把模型输入路径、目标平台、量化策略和输出位置变成参数或配置文件，适合批处理和 CI，但并不会自动修正错误的训练前处理。不同 release 的 `rknn_convert` 参数、配置字段可能变化，因此运行前看同版本 `--help` 和官方示例比背口播命令更可靠。

**理解判据：** 首先核查实际安装的是哪个可执行文件、属于哪个 SDK release。

### 配置文件要留下审计痕迹

转换配置至少应含输入模型来源与 SHA256、target_platform、输入 layout、量化开关、校准数据位置和输出路径。相同文件名可能被覆盖，生成后还要记录转换日志和模型文件哈希值，便于复现与回滚。

**理解判据：** 将配置和输出 hash 一起提交版本库，避免把不同构建混为一谈。

### 设计一个可重复批量转换流水线

一个健壮的脚本先做参数合法性与文件存在性检查，再调用转换、保存 stdout/stderr、检查退出码和输出文件；最后执行固定样本的精度验证。仅看 shell 返回 0，无法判断转换后业务语义是否正确。

**理解判据：** 转换自动化以‘构建通过 + 语义回归’两个条件判断是否合格。

## 实操实验

### 实验 1：核对 CLI 版本

在匹配 SDK 环境里先检查 `which rknn_convert` 与帮助信息（若该 release 提供此命令）；找不到则使用 SDK 的 Python 示例。

**应该检查：** 确认使用的是已经安装的真实工具，并保存帮助页面和版本。

### 实验 2：准备转换任务单

为一个 ONNX 模型建立 src_model、target、dtype、quantize、calibration、output、sdk_version 的表格。

**应该检查：** 任务单里每一项有确定值或明确的‘不适用’。

### 实验 3：添加产物校验

转换前计算源 ONNX 的 SHA256；转换后计算 RKNN 的 SHA256 并归档日志。

**应该检查：** 至少有一个可解释的输入到输出的追踪链。

### 参考代码与命令

```bash
sha256sum model.onnx
# 如当前 SDK 提供 CLI：先执行 rknn_convert --help
# 再根据该版本参数转换模型，而不是臆造选项。
sha256sum model.rknn
```

> 参考示例会依赖具体模型、SDK 和设备设置；请先确认文件路径、输入协议与运行条件。

## 诊断常见问题

### 复制命令却提示未知参数

- 可能原因：参数来自另一版 `rknn_convert`。
- 如何验证：查当前 SDK 的 `--help`，不要在无法验证的情况下猜测选项名称。

### 同一条命令重复输出不同结果

- 可能原因：模型来源变化、校准集变化或安装依赖未固定。
- 如何验证：对比输入 SHA256、校准列表、SDK 版本及转换日志。

## 案例推理

**场景：** 你在自动化系统中每次生成 `model.rknn`，文件名一样但某周精度骤降，怎样回溯？

**分析：** 查看该构建的源模型 hash、校准数据清单、SDK tag、转换参数和输出 hash，再使用保存的验证集运行回归测试。没有这些数据就很难定位。

**需要的证据：** 每次构建的 manifest、日志与量化/非量化对照结果。

## 源码精读：关键 API、张量与验收

第 11 讲的 lesson_11.py 是一个小型批量转换器：从 JSON jobs 依次调用同一个 convert_onnx.py，保存每个模型的实际转换日志。它不是替代 RKNN-Toolkit2 的魔法转换格式。

**数据路径：** `jobs.json` → `单项 ONNX + mean/std` → `convert_onnx.py` → `task_XX.log` → `manifest.json`。

### 1. jobs.json：每个转换任务的输入协议

**输入：** 数组内每项包含 onnx、output、mean、std。**输出：** 明确文件名与可选 quantize/dataset 的任务表。

model.onnx 需要真实存在；mean/std 要根据该图的训练输入规定填写，不能把所有模型统一写成 0/1。

```json
[
  {"onnx":"build/tiny.onnx","output":"build/tiny.rknn","mean":"0,0,0","std":"1,1,1"}
]
```

### 2. subprocess.run：逐项执行官方 Toolkit2 API 封装

**输入：** 转换任务 cmd 数组。**输出：** 真实 exit_code 与 stdout/stderr 合并日志。

转换器实际调用 config/load_onnx/build/export_rknn，失败会记入日志并导致脚本退出非零。日志成功不一定表明 RK3588 能跑。

```bash
python3 examples/lesson_11.py --jobs /path/to/jobs.json --log-dir build/lesson11
```

### 3. manifest.json：分清成功和失败

**输入：** 每项返回码、模型输出路径和日志路径。**输出：** 每个任务的运行摘要；不能反推出真实量化精度。

转换通过后还要跑后续模拟/板端推理，并用相同输入做数值或任务指标对照。INT8 必须有代表性校准数据。

```bash
python3 -c "import json; print(json.load(open('build/lesson11/manifest.json')))"
```

**数据例题：** 同一项目 2 个模型：A 转换成功、B 因不支持算子失败。manifest 必须保留两项不同 exit_code，不得只保留成功的 A 再声称全部模型可部署。

**验收边界：** 在具备 Toolkit2 的真实主机上保存逐任务日志、输出模型及成功/失败清单；在无 Toolkit2 时先完成 JSON 配置理解。
