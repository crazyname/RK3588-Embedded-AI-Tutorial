## 学习目标

- 合理分离主程序、模型封装、预处理和后处理

- 统一日志、错误处理与资源释放

## 核心原理与工程设计

### 把演示代码分成职责清晰的模块

分类应用至少有模型管理、输入预处理、推理执行、输出后处理、资源文件与日志六类职责。不要把 RKNN 初始化、图片读取、分类结果格式化都挤进 `main`；这样每次更换模型都容易误改接口。推荐将‘模型输入协议’和‘类别映射’封装为可验证的数据结构。

**理解检查：** 模块输入输出、错误返回和资源所有权都必须在接口文档中声明。

### 生命周期与 C++ RAII

用构造函数获取、析构函数释放资源可以减少 C API 在异常路径中的泄漏风险；同时需要考虑初始化失败的对象状态和禁止错误拷贝持有 RKNN context 的类。线程之间共享模型上下文是否安全，应以 SDK 文档为准，不能未经验证假设。

**理解检查：** 模型对象应提供明确 init/infer/reset 语义，并保证重复销毁安全。

### 分层测试和版本回归

预处理单测可检查像素、resize 后 shape；后处理单测可用固定 scores 校验 top-k；真实推理集成测试用保存的样例图和 label 输出。升级 SDK、换量化模型或变更图像库后，先运行单元测试，再上板测试与压力测试。

**理解检查：** 能够不用启动 NPU 就验证大部分业务逻辑，缩小真实硬件调试范围。

## 排错技巧

### 出现双重释放或崩溃

- 根因：资源所有者不明确、包含上下文的对象被错误复制。
- 如何核对：检查构造/析构路径，必要时禁止 copy 并明确 move 语义。

### 更新预处理后分类结果变化

- 根因：库版本、插值方式或通道布局被悄然改动。
- 如何核对：保存输入 tensor 的回归测试和比较阈值。

## 工程案例

**情境：** 封装类在函数返回后崩溃，原因是两个对象持有同一个 rknn_context 并在析构中销毁。应如何设计？

**分析过程：** 让上下文拥有单一所有权，禁止复制或正确实现移动语义；封装初始化失败状态与显式释放。在需要多实例时，为每个实例清楚指定 SDK 允许的上下文创建/线程调用方式。
